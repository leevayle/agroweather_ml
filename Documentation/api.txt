5. API STARTUP AND PERFORMANCE
==============================

When FastAPI starts, api.py imports forecast_engine.py.
The trained ML models are loaded into memory once.

The intended flow is:

    API starts
        |
        +--> load ML models into RAM
        |
        +--> start server
        |
        +--> serve requests

Models should not be loaded from disk for every request.

The normal forecast is also cached, so repeated requests do not
unnecessarily recalculate the same forecast.

7. GET /
=========

Purpose:
    Returns the latest current-weather data held by the backend.

Request:

    GET /

Example:

    http://127.0.0.1:8000/

Example response:

    {
      "status": "success",
      "type": "current_weather",
      "data": {
        "temperature_c": 21.7,
        "humidity_percent": 78.4,
        "day_night": "day",
        "rainfall_mm": 2.3,
        "rain_status": "raining",
        "wind_speed_kmh": 9.8,
        "wind_direction": "NE",
        "pressure_hpa": 1014.8,
        "timestamp": "2026-09-24T18:35:12",
        "source": "ESP32"
      }
    }

Important fields:

    temperature_c
        Current temperature in Celsius.

    humidity_percent
        Current relative humidity percentage.

    day_night
        Day/night state.

    rainfall_mm
        Current/recent rainfall measurement.

    rain_status
        Human-readable rain state.

    wind_speed_kmh
        Current wind speed.

    wind_direction
        Current wind direction.

    pressure_hpa
        Atmospheric pressure in hPa.

    timestamp
        Time the backend last received the reading.

    source
        Current data source, normally ESP32.

If no sensor data is available, values may be null:

    "temperature_c": null

The frontend should show something such as:

    Waiting for station data...

or:

    --

10. GET /forecast?days=N
========================

Purpose:
    Requests a specific number of forecast days.

Example:

    http://127.0.0.1:8000/forecast?days=7

Supported range:

    Minimum: 1 day
    Maximum: 30 days

Examples:

    /forecast?days=5
    /forecast?days=7
    /forecast?days=14
    /forecast?days=30

Invalid:

    /forecast?days=0

Expected:
    HTTP 400 Bad Request

Invalid:

    /forecast?days=31

Expected:
    HTTP 400 Bad Request


11. FORECAST RESPONSE FIELDS
============================

Each forecast day contains:

    date
        Forecast date in YYYY-MM-DD format.

    temperature.avg_c
        Predicted average temperature in Celsius.

    temperature.min_c
        Predicted minimum temperature in Celsius.

    temperature.max_c
        Predicted maximum temperature in Celsius.

    rainfall.rain
        Boolean indicating whether rain is predicted.

    rainfall.probability
        Model probability from the rain/no-rain classifier.
        Example: 0.82 means an 82% model probability, not a
        guarantee.

    rainfall.amount_mm
        Predicted rainfall amount in millimetres.

    wind_speed
        Predicted wind speed.

    pressure_hpa
        Predicted pressure in hPa.


12. GET /forecast/range
=======================

Purpose:
    Requests a forecast for a specific date range.

Format:

    GET /forecast/range?start_date=YYYY-MM-DD&end_date=YYYY-MM-DD

Example:

    http://127.0.0.1:8000/forecast/range?start_date=2025-11-01&end_date=2025-11-07

This requests 7 days.

Response:

    {
      "status": "success",
      "start_date": "2025-11-01",
      "end_date": "2025-11-07",
      "forecast_days": 7,
      "forecast": [
        ...
      ]
    }

Date format must be:

    YYYY-MM-DD

Correct:

    2025-11-01

Incorrect:

    01/11/2025


13. FORECAST RANGE LIMIT
========================

Maximum range:

    30 days

Example of a valid 30-day request:

    /forecast/range?start_date=2025-11-01&end_date=2025-11-30

A range longer than 30 days returns:

    HTTP 400 Bad Request


14. FORECAST BEHAVIOUR
======================

The current ML system is recursive.

Conceptually:

    Day 1 prediction
        |
        v
    helps predict Day 2
        |
        v
    helps predict Day 3
        |
        v
       ...

Because predictions are reused for later predictions, uncertainty
can accumulate over longer forecast horizons.

Forecasts are model predictions, not guarantees.

21. PERFORMANCE DESIGN
======================

ML models:

    Loaded once at API startup
        |
        v
    kept in RAM
        |
        v
    reused by requests


Current weather:

    latest reading
        |
        v
    in-memory current_weather
        |
        v
    GET /


Normal forecast:

    first request
        |
        v
    forecast calculation
        |
        v
    cached in RAM

Later requests:

    GET /forecast
        |
        v
    cached result


This prevents repeated disk model loading and unnecessary
forecast calculations.

27. DEVELOPMENT RULES
=====================

1. Never invent current weather values when the station has no data.
   Use null and let the frontend show a loading/offline state.

2. Keep ML models loaded in memory.

3. Keep normal forecast results cached.

4. Use /forecast/range for custom date ranges.

5. Do not expose the development server directly to the public
   internet.

6. Humidity and wind direction should remain live measurements until
   enough historical data exists to train models for them.

7. The current CSV-based forecast is a development-stage system.
   The production system should use MongoDB and current station data.

8. Forecast values are predictions, not guarantees.

9. Keep this document as the backend API reference while building
   the AgroWeather frontend.


28. POST /chat
==============

Purpose:
    Sends a farm-related message to the authenticated AgroWeather
    assistant. The backend adds the user's saved farm details and
    available current weather/forecast context.

Authentication:
    Include the bearer token returned by /auth/login or /auth/signup:

    Authorization: Bearer YOUR_ACCESS_TOKEN

Request:

    POST /chat
    Content-Type: application/json

    {
      "message": "Will it rain on my maize this week?",
      "history": [
        {
          "role": "user",
          "content": "I grow maize."
        },
        {
          "role": "assistant",
          "content": "I can use your saved farm details and available forecast."
        }
      ]
    }

Response:

    Content-Type: text/event-stream

    event: token
    data: {"text":"The forecast shows..."}

    event: token
    data: {"text":" Protect your maize from heavy rain."}

    event: done
    data: [DONE]

    Provider failures are sent as a friendly `error` event followed by
    `done`. Detailed provider diagnostics are written only to the backend
    log.

Gemini configuration:
    Set GEMINI_API_KEY in the root .env file. GEMINI_MODEL is
    optional and defaults to gemini-3.8-flash, which is listed as free of
    charge on Google's Free tier. Free-tier usage is subject to Google's
    model availability and rate limits. Chat uses Google's Interactions API
    and does not ask Google to store conversation requests. Restart the
    backend after changing the configuration. Never put the provider key
    in frontend code.

Errors:
    Before streaming:
        401 - missing or invalid access token
        422 - invalid or empty message
        503 - assistant configuration unavailable
    During streaming:
        event: error - friendly message for usage limits or temporary issues
        Detailed Gemini diagnostics are available only in the backend log.


    29. GET /chat/insights
    ======================

    Purpose:
        Returns Gemini-generated recommendations for the authenticated
        user's saved crops, informed by up to 24 readings from the previous
        seven days, the latest available station reading, and up to seven
        forecast days.

    Authentication:
        Include the bearer token returned by /auth/login or /auth/signup:

        Authorization: Bearer <access_token>

    Response:

        {
          "insights": [
            {
              "crop": "Maize",
              "headline": "Plan field work around the coming rain.",
              "activities": [
                {
                  "activity": "Check soil moisture before irrigating.",
                  "timing": "Before the next forecast rain",
                  "reason": "Recent and forecast rainfall can affect field moisture."
                }
              ],
              "optimal_conditions": "Keep soil moisture suitable for the crop's current stage.",
              "harvest_guidance": "Check crop maturity indicators; planting date and growth stage are not available."
            }
          ]
        }

        The response includes one recommendation for each saved crop.
        Weather-based claims are grounded in available data; harvest readiness
        is not inferred when planting date and growth stage are unknown. Missing
        weather data is passed to the assistant as unavailable, not fabricated.

    Errors:
        401 - missing or invalid access token
        429 - Gemini usage limit reached
        503 - assistant configuration or provider unavailable


    30. POST /calendar/tasks
    ========================

    Purpose:
        Saves a recommended crop activity to the authenticated user's
        AgroWeather calendar. Repeated requests for the same crop, activity,
        and timing do not create duplicate tasks.

    Authentication:
        Include the bearer token returned by /auth/login or /auth/signup:

        Authorization: Bearer <access_token>

    Request:

        POST /calendar/tasks
        Content-Type: application/json

        {
          "crop": "Maize",
          "activity": "Clear and maintain field drainage channels",
          "timing": "2026-10-30",
          "reason": "Reduce the risk of waterlogging ahead of forecast rain."
        }

    Response:

        {
          "message": "Task added to your calendar.",
          "created": true,
          "task": {
            "id": "MongoDB object ID",
            "crop": "Maize",
            "activity": "Clear and maintain field drainage channels",
            "timing": "2026-10-30",
            "reason": "Reduce the risk of waterlogging ahead of forecast rain.",
            "date": "2026-10-30",
            "status": "planned",
            "created_at": "2026-10-29T14:00:00+00:00"
          }
        }

        A repeated request returns `created: false` and reports that the task
        is already in the calendar. Tasks are stored in the `calendar_tasks`
        MongoDB collection and associated with the authenticated user.

    Errors:
        401 - missing or invalid access token
        422 - missing or invalid task information
        503 - calendar storage is temporarily unavailable


    31. GET /calendar/tasks?start=YYYY-MM-DD&end=YYYY-MM-DD
    ==========================================================

    Returns the authenticated user's tasks in the requested date range,
    plus tasks that do not yet have a date. The maximum date range is
    100 days.

    Response:

        {
          "tasks": [
            {
              "id": "MongoDB object ID",
              "crop": "Maize",
              "activity": "Check soil moisture",
              "timing": "2026-10-30",
              "reason": "Check before irrigation.",
              "date": "2026-10-30",
              "status": "planned",
              "created_at": "2026-10-29T14:00:00+00:00"
            }
          ]
        }

    32. PATCH /calendar/tasks/{id}
    ==============================

    Updates one task owned by the authenticated user. Send any combination
    of `crop`, `activity`, `reason`, `date` (YYYY-MM-DD), or `status`
    (`planned` or `completed`).

    Example:

        {
          "date": "2026-10-31",
          "status": "completed"
        }

    33. DELETE /calendar/tasks/{id}
    ===============================

    Deletes one task owned by the authenticated user. Returns
    `{"deleted": true}` when successful.

    34. PUT /auth/me/station
    =======================

    Saves the station code for the authenticated user's farm. A newly
    selected station replaces the previous station code.

    Authentication:
        Include the bearer token returned by /auth/login or /auth/signup.

    Request:

        PUT /auth/me/station
        Content-Type: application/json

        {
          "station_code": "station_01"
        }

    Station codes may contain letters, numbers, hyphens, and underscores.
    The response is the updated user profile.

    35. GET /weather/current?station_id={station_id}
    ===============================================

    Optionally filters the current reading to the requested station ID.
    If no reading is available for that station, the response has
    `status: "waiting_for_data"` and includes the requested station ID.
